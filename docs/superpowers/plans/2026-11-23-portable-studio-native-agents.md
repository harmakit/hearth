# Переносимая студия · план реализации

> Исполнять в основной сессии через `superpowers:executing-plans`. Субагенты могут независимо проверять отдельные этапы. Шаги отмечаются по результатам проверок.

**Цель.** Открывать полную копию проекта с той же студией и выполнять задачи с нативными ролями и навыками Claude Code и Codex.

**Архитектура.** Настройки и нативные определения читаются из проекта. Каждая студия хранит рабочее состояние в собственной SQLite, а профиль приложения содержит пользовательские настройки и список подключённых путей. Git выполняет операции над рабочими копиями и ветками, Hearth хранит решения студии и контролирует выполнение.

**Стек.** Electron, Node.js SQLite, Git CLI, Claude Code, Codex App Server, `node:test`.

**Спецификация.** [Переносимая студия](../specs/2026-11-23-portable-studio-native-agents.md).

## Общие ограничения

- Работа только в новом Hearth Studio. Нативные прогоны используют временные профили и проекты в его `.tmp`.
- В Git по умолчанию попадают обычные файлы проекта и только настройки, инструкции и навыки Hearth. Состояние, память и рабочие копии остаются в копии папки.
- Пользователь подтверждает доверие новой папке перед первым запуском. При переносе сохраняются идентификаторы, незавершённые изменения и гарантии приёмки.
- Частные данные соседних задач, текущее состояние и Git-метаданные защищены от запущенного исполнителя. Внутренний путь рабочей копии не расширяет права на родительский проект.
- Каждый этап начинается с падающих проверок, заканчивается целевыми зелёными тестами и отдельным коммитом. Платформы без провайдера проходят системный сценарий с тестовым исполнителем.

## На что смотреть при ревью

1. Прерывание между готовностью файлов и переключением активного пути оставляет одну активную очередь. Закрепить на этапе 4.
2. Относительная ссылка на локальный навык разрешается из самой рабочей копии. Ссылка наружу отвергается. Закрепить на этапах 2 и 3.
3. Приватная запись уже находилась в индексе Git. Hearth обнаруживает её и ждёт подтверждения. Закрепить на этапе 2.
4. Рабочая копия находится внутри проекта, а её прежний абсолютный путь всё ещё доступен. Ремонт меняет только копию. Закрепить на этапах 3 и 5.
5. Копия содержит ожидающее слияние к старой ветке и остановленный запуск. Результат повторно сверяется, слияние не повторяется автоматически. Закрепить на этапах 4 и 5.

При отсутствии обоих способов запуска роли в Codex остановить этот этап с конкретной несовместимостью.
- [ ] Тест `native role and input skills preserve the granted scope` проверяет `--agent <role>`, корректный запрос App Server и отказ при пропущенном или подменённом обязательном навыке. ## 4. Хранилище по студиям и безопасная миграция

**Файлы.** Новый `core/studio-storage.mjs`, подключение в `core/service.mjs`, `app/main.cjs`, `app/transfer.mjs`. Тесты в `test/studio-storage.test.mjs`, `test/transfer.test.mjs` и `test/app-transfer.test.mjs`.

**Интерфейс.** `openStudioStorage(root, {expectedStudioId})` открывает `.hearth/state/studio.sqlite3` с существующей схемой студийных данных. `inspectStudioMigration({studioId, root})` возвращает план переноса с ревизией. `migrateStudio({studioId, root, expectedRevision})` записывает данные и переключает активный путь только после проверки. `prepareStudioCopy({studioId})` подтверждает возможность безопасного копирования.

- [ ] Тест `migration preserves relational data and private bytes without copying global settings` сравнивает данные таблиц, пары событий истории, ID, хеши вложений и квитанции. Тест `retry after failure at each migration phase activates at most one copy` прерывает процесс до создания БД, после записи, после перемещения рабочих копий и перед переключением. Тест `copy preparation does not mark unresolved provider work complete` сохраняет состояние прерванной попытки и уже применённое решение.

Учесть ссылки, которые сейчас встроены в записи материала, вложения, доказательства, состояние доставки и черновики в локальном хранилище интерфейса.
- [ ] Реализовать подготовку к копированию через штатную паузу и завершение файловых операций. В БД хранить пути относительно проекта. Для миграции использовать исходное хранилище в качестве резерва, журнал прогресса и проверку выбранной папки перед переключением. Сохранить поддержку старых экспортных файлов.
