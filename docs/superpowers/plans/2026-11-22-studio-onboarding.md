# Первый запуск Hearth Studio · план реализации

> После согласования спецификации выполнить в основной сессии через `superpowers:executing-plans`. Пункты ниже — черновик для обсуждения. На этапе проектирования исходники приложения не меняются.

**Цель.** Провести владельца от первого запуска до своей студии, согласованного плана и первого проверенного результата.

**Архитектура.** Существующий нативный мастер сохраняет поля и вызывает текущую команду создания студии. Карточка «Начало работы» выводит следующее действие из сохранённого состояния студии, провайдеров, плана и задач. Действия ведут к обычным рабочим экранам и сохраняют текущие серверные правила.

**Стек.** Electron, HTML, CSS, модули ESM, Node.js 24+, `node:test`, существующий нативный сценарий QA.

**Спецификация.** [Первый запуск Hearth Studio](../specs/2026-11-22-studio-onboarding.md) · [Макет](../../reviews/studio-onboarding.html).

## Общие ограничения

- Английский по умолчанию. Все видимые статусы, поля, ошибки и доступные имена переведены для `en`, `zh-Hans`, `es`, `fr`, `ru`.
- Один черновик на профиль, восстановление версии 1. Первая задача необязательна. Для новой папки сохраняется локальная история и ветка Git. Существующий Git подключается отдельно по выбору владельца.
- Начальная команда, учёт зависимостей, план, ревью и приёмка используют существующие реализации. При открытии мастера, записи черновика и создании студии агент не запускается.
- Общие токены движения 100 и 140 мс, `prefers-reduced-motion`, видимые доступные элементы сразу. Минимум окна 590 × 470 и увеличение 200%.
- Проверка в отдельном профиле `HEARTH_DATA_DIR`, с временными проектами в `.tmp` и подставным провайдером. Профили и папки предыдущей Hearth не участвуют.

## Что проверить особенно внимательно

- Смена языка при незавершённом черновике оставляет пользовательские поля и явный выбор провайдера.
- Прерванное создание Git-папки и потерянный ответ после записи студии приводят к разным действиям.
- Обнаружение нового доступного провайдера не переписывает выбор владельца.
- Завершение учебного упражнения и появление стартового файла не означают готовый рабочий результат.
- В ветке Git с режимом удержания видна ожидающая версия до решения, затем подтверждённый результат.

## 2. Мастер, черновик и создание

**Файлы** `renderer/app.mjs`, `renderer/onboarding-view.mjs`, `renderer/studio-draft.mjs`, `test/studio-draft.test.mjs`, `test/app-bridge.test.mjs`, `test/renderer-onboarding-view.test.mjs`.

**Используемые команды** `createStudio(payload)`, существующий выбор пути, переключение модели директора и `inspectProvider({ runtime })`. Разметка шага получает явно выбранные значения, переключатель способа создания и наблюдаемый статус проверки.

- [ ] В тестах добавить восстановление черновика с каждым шагом, проверку первой задачи, различие между ручным/предложенным провайдером, отказ записи и сохранение защиты `pending`. В нативном QA зафиксировать недостающий фокус и ошибки. Запустить `node --test test/studio-draft.test.mjs test/app-bridge.test.mjs test/renderer-onboarding-view.test.mjs` и подтвердить ожидаемые ошибки новых проверок.
- [ ] Собрать шаги в текущем `dialogTo`, сохранить явный выбор и эффективную конфигурацию. Хранить `runtimePicked`, если версия черновика без этого признака читается как раньше. Сохранять уже выбранное в версии 1 подключение как явное при миграции, потому что старый формат не различал источник выбора. При проверке провайдера обновлять статус без пересборки поля и сброса фокуса. Для явно недоступного подключения дать создать студию без запуска.
- [ ] Различать ошибки валидации и неопределённый исход команды. Существующее сообщение неизвестного исхода разрешает безопасную сверку. При подтверждённом результате перейти к студии по её ID. После успеха предложение Git выводится без захвата фокуса в «Обзоре», подтверждение ветки идёт через существующий редактор. Если данные выбранного провайдера меняются во время ожидания, отобразить последний результат проверки.
- [ ] Повторить целевые тесты. Проверить существующие маршруты новой Git-папки, обычной папки и старой Hearth. Если типизированный признак ошибки нужен, добавить его в ответ узкой команды проверки/создания и сохранить общую защиту выбранной папки.
