# Hearth Studio · план реализации рабочего места владельца

**Черновик на согласование · 19 ноября 2026.** Выполнение начинается после явного одобрения владельцем [спецификации](../specs/2026-11-19-owner-workspace-design.md) и этого плана. При выполнении по задачам применяются Superpowers Subagent-driven Development либо Executing Plans. Отметки ниже предназначены для будущей реализации.

**Цель.** Владелец находит работу, требующую решения, видит причины и доказательства, принимает решение и возвращается к той же задаче с понятным результатом.

**Архитектура.** Core и диспетчер отвечают за факты и переходы состояний, Electron main — за доступ к файлам и доставку. Renderer получает связанные объекты по ID, рисует общие строки, инспектор и формы. Новую историю пишем рядом с исходным изменением. Предпочтительны существующие команды сервиса и транзакции.

**Стек и база сравнения.** Electron, JavaScript ESM, SQLite, встроенный Node test runner. Исторически проверенная ревизия отдельного репозитория приложения — `3998a54`, ветка `workspace-settings`, версия 0.3.3. Пути ниже относительны к корню **приложения**. Папка игры в текущем рабочем каталоге — другой проект. Исходники приложения сейчас отсутствуют по прежнему пути. Названия существующих модулей сверены по аудиту и истории сборки; целевые контракты ниже предложены для реализации.

## Порядок и критические проверки

Первая демонстрация после одобрения — один полный маршрут «решение → проверенная версия → файл → принятие или возврат». Сначала установить базовую линию, затем связать факты, сделать общий инспектор и пройти этот маршрут. Далее — первый запуск, рабочие разделы, настройки и сквозная приёмка. После каждого среза получается отдельно проверяемое изменение.

| Где вероятна ошибка | Где она должна быть поймана |
|---|---|
| У двух студий совпадают короткие ID, обновление приходит во время ввода | Шаги 1, 2, 4 и 6. Проверить пару studioId + objectId и сохранение черновика. |
| Принята устаревшая ревизия или случился сбой посередине доставки | Шаг 3. Проверить расхождение базы, двойную отправку, повтор после перезапуска. |
| Неизмеренный расход выглядит как ноль, кэш прибавлен ко входу дважды | Шаги 1 и 6. Смешанные форматы Codex/Claude, частичное покрытие и повторный импорт событий. |
| Очистка worktree или перенос проекта ломает историческую ссылку | Шаги 3 и 7. Сохранённая квитанция, пропавший путь, доступ за пределами разрешённого корня. |
| «Прочитано» скрывает работающий блокер; согласование спринта внезапно запускает лишние задачи | Шаги 4 и 5. Проверить несколько открытых причин, train и устаревший план. |

**Цикл проверки каждого изменения.** Сначала тест, который воспроизводит указанное расхождение; убедиться, что он падает по ожидаемой причине. После изменения прогнать этот же тест и `npm test`. Сохранять самостоятельно работающий срез отдельным коммитом в ветке приложения. Прогоны используют временный профиль тестового проекта и имитаторы провайдеров. Новые файлы тестов ниже — предлагаемые имена.
