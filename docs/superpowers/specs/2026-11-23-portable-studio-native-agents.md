# Переносимая студия · штатные роли, навыки и рабочие копии

**На согласование.** Папка проекта содержит всю студию. В Git по умолчанию попадают обычные файлы проекта и только три вида студийных материалов: настройки, инструкции и навыки.

## Что увидит владелец

- При создании студии Hearth сохраняет её настройки и роли в выбранную папку. После принятия обучения руководство и навыки можно прочитать в Finder, редакторе или Hearth. Принятое упражнение и обоснование остаются доступны в истории задачи.
- Для переезда владелец закрывает Hearth или приостанавливает работу и ждёт готовности к копированию. Затем копирует всю папку, включая скрытые файлы и `.git`, и выбирает **«Открыть папку студии»** на другом компьютере или по новому пути. Hearth открывает ту же студию с её очередью, историей, результатами и незавершённой работой. Открытие не запускает процессы. После проверки папки владелец возобновляет работу обычным действием студии.
- Чистый Git-клон содержит рецепт студии: настройки, роли, инструкции и навыки. Hearth может открыть этот рецепт с пустой локальной историей. Если оригинал и полная копия открываются в одном профиле, Hearth показывает оба пути и предлагает явно переключиться. Очередь одной записи обслуживается в одном выбранном месте.
- Для существующих студий приложение предлагает **«Перенести данные в папку»** с предварительным просмотром. При переносе сохраняются ID, решения, транзакции приёмки, вложения и изменения в рабочих копиях. До успешной проверки прежнее хранилище остаётся доступно для восстановления.

## Какие данные где лежат

| Путь | Содержимое | Git по умолчанию |
|---|---|---|
| `.hearth/studio.json` | Версия формата, ID и имя студии, настройки спринтов, моделей, команды, проверок и доставки. Параметры, зависящие от машины, задаются в приложении по месту. | Да |
| `.hearth/roles/<role>.md` | Общая инструкция роли, имя, описание и обязательные навыки. Принятое руководство коуча становится частью инструкции роли. | Да |
| `.agents/skills/<skill>/SKILL.md` | Основной экземпляр навыка с обычными `name` и `description`. В папку навыка входят принятые справочные материалы, разрешённые лицензией. | Да |
| `.claude/agents/<role>.md`, `.codex/agents/<role>.toml`, `.claude/skills/<skill>` | Штатные определения ролей и доступ к общему навыку. | Да |
| `.hearth/state/`, `.hearth/worktrees/` | База студии, журнал задач, спринтов и решений, учебные упражнения, приватная память и заметки, вложения, свидетельства проверок, черновики, рабочие копии и квитанции доставки. | Исключены |
| Обычные папки проекта | Опубликованные результаты, включая двоичные файлы и изменения после Git-доставки. | По правилам проекта |
| Профиль приложения | Реестр путей студий, язык интерфейса, уведомления, состояние подключений, локальные разрешения, учётные данные и восстанавливаемые кэши. | Вне проекта |

Правила игнорирования ограничены служебными путями Hearth и управляемой приватной памятью. Существующие исключения и индекс проекта сохраняются. Файлы, которые уже отслеживаются, показываются в предварительном просмотре: Hearth просит подтвердить изменение индекса и не меняет историю репозитория. Пароли, токены, авторизация провайдеров, пути к личным бинарникам и настройки удалённого исполнителя не записываются в настройки студии для Git.

## Штатные роли и навыки

- Hearth хранит инструкцию роли в одном читаемом источнике и формирует Markdown Claude Code с `skills` и TOML Codex с `developer_instructions`. Штатные файлы пригодны для самостоятельного запуска из репозитория. При подключении существующего проекта Hearth показывает найденные роли и конфликты имён. Чужие поля, файлы и ручные правки не перезаписываются молча. Управляемый файл с внешними правками ждёт решения владельца.
- Claude Code запускается с `--agent <role>` и использует свой список предварительной загрузки. Codex получает роль через проверенный нативный стартовый контракт. Первый шаг реализации проверяет установленный App Server. Если он пока не выбирает верхнеуровневую роль по имени, Hearth использует `developerInstructions` из её TOML через поддерживаемое поле старта сессии, а TOML по-прежнему доступен как штатная роль Codex. Если нет и проверенного способа передать инструкции уровня разработчика, запуск с этой ролью сообщает о несовместимости. Обязательные навыки передаются Codex как штатные элементы `skill` с путями, подтверждёнными `skills/list` для текущей рабочей копии.
- `description` описывает, когда применять навык. Для дополнительных навыков остаётся обычное обнаружение провайдером. Hearth прекращает отбор навыков по словам задачи и подстановку полного текста в пользовательский запрос. Задача, критерии, решения владельца и рабочие материалы по-прежнему передаются как контекст задачи. Если обязательный навык отсутствует или не открывается, Hearth показывает имя и причину перед запуском.
- В macOS и Linux Claude видит отдельные относительные ссылки на каталоги навыков. В Windows, когда создание ссылок недоступно, Hearth публикует обычный каталог из проверенного общего источника. В журнале запуска видно, какая роль выбрана и какие обязательные навыки подключены. Применение навыка показывается только при подтверждении от провайдера.
- Коуч продолжает находить, готовить и проверять материалы. При принятии Hearth публикует руководство и навыки как проектные файлы. Для стороннего навыка фиксируются URL, ревизия и лицензия. Файлы с неподтверждённым правом на повторное распространение остаются частным материалом студии. У старых навыков без `description` используется подтверждённая формулировка из роли или обучения, а при её отсутствии приложение предлагает дополнить описание. Оригинал сохраняется. Память роли доступна обоим инструментам через инструкции роли и хранится в приватной части папки. Claude может использовать штатную проектную память, если её местоположение включено в приватные пути и перенос.
- Данные служебной папки и соседних рабочих копий закрыты от исполнителя. Для чтения рабочего контекста используются отдельный рабочий корень и явно разрешённые материалы.
- Подключение папки не считает её доверенной автоматически на новом компьютере. Обычный запуск сохраняет утверждённую границу чтения и записи, сетевые ограничения и ограничения инструментов. Настройки роли из Git не меняют их.

## Рабочие копии, перенос и восстановление

- При запуске в рабочей копии Hearth использует утверждённую версию файлов роли и навыков. Служебно подготовленные для запуска файлы не подмешиваются в результат задачи. Если на ветке уже лежит другой вариант управляемых файлов, Hearth сообщает о конфликте. Файлы роли и навыков попадают в Git через явное сохранение проекта.
- Использовать обычные Git worktrees по `.hearth/worktrees/<id>` для задач и вложенный каталог для временных проверяемых копий. Для связанных рабочих копий с относительными путями нужен Git 2.48 или новее. Ветка задачи, подтверждённая ревизия, кандидат, проверки, приёмка и правила локального слияния сохраняют свои гарантии. Глобальный профиль больше не нужен, чтобы найти ожидающие приёмки изменения.
- Сохранять пути проекта и рабочей копии относительно корня. При открытии перемещённой или скопированной папки сверять `.git`, зарегистрированные рабочие копии, ветки и ссылки на проверенные ревизии. Восстанавливать связи только внутри выбранной папки штатным `git worktree repair`, если ссылки требуют обновления. Содержимое рабочей копии, индекс, незакоммиченные и неотслеживаемые файлы должны переживать эту операцию. Внешний связанный чек-аут, внешние Git-объекты и отсутствующие файлы определяются до обещания полной переносимости. Для них Hearth предлагает подготовить самостоятельную папку и сохраняет исходную.
- По завершении подготовки к копированию Hearth прекращает новые запуски, приводит БД к консистентному состоянию и завершает файловые операции. Открытие копии восстанавливает очередь, ожидающие ответы и историю. Прерванный живой процесс становится записью для безопасного продолжения. Приложение не повторяет автоматически неизвестное внешнее действие, уже применённое решение или слияние.
- Миграция сохраняет полный набор записей студии, файлы и журнал до переключения активного пути. Повтор после сбоя безопасен. Внести отдельную проверку исходной папки и копии в разных профилях. При проблеме Hearth показывает, какие данные требуют внимания, и оставляет их на месте.

## Приёмка

1. В чистом временном проекте создать студию, подготовить роль и принять навык с дополнительным справочным файлом. Подтвердить, что оба настоящих инструмента читают нужную роль и загружают обязательный навык из соответствующей рабочей копии. Переключить роль с одного провайдера на другой. Для Windows и Linux системные проверки проходят с временными профилями и тестовым исполнителем, установка Claude или Codex для них не требуется.
2. Проверить реальный Git-клон из локального репозитория. В нём есть файл настроек, роли и навыки. Статусы, приватная память, вложения, учётные данные и рабочие копии отсутствуют. Состав коммита проверяется в Git, а не по отображению файлового менеджера.
3. В копии полного проекта по другому пути и с чистым профилем открыть текущий спринт. Сверить решения и отчёты, ожидающую приёмку ревизию, незакоммиченный и неотслеживаемый файл, затем завершить приёмку и слияние. Убедиться, что операция затронула только копию.
4. Повторить перенос старого формата после намеренного прерывания. Проверить два одинаковых ID, существующие настройки Claude/Codex, путь с пробелами, недоступность ссылок на Windows, отсутствующую ссылку Git и подмену ссылки на каталог за пределами проекта.
